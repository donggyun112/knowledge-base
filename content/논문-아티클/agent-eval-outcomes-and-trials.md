# 에이전트 평가 설계 — 완료 주장·상태 변화·반복 신뢰성

도구를 쓰는 에이전트를 평가할 때는 **답변, 외부 상태, 실행 환경을 어떤 증거로 연결할지** 먼저 정해야 한다. 이 글은 새로운 judge 알고리즘보다 평가 운영의 설계 기준을 살펴볼 자료다.

- **원문**: [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents), Anthropic Engineering
- **발행일**: 2026-01-09. 별도 수정일은 원문에 미표기. 최신 발표가 아니라 기존 핵심 자료의 수집이다.
- **기존 주소**: [engineering 경로](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)는 확인 시 위 research 경로로 이동했다.
- **수집일**: 2026-11-12 KST
- **상태**: Techniques / Assess / 읽기 전
- **검증 범위**: 공개 원문 본문 검토. 평가 도구 설치, 모델 호출, 실행·재현 실험은 하지 않았다.

## 원문의 핵심

- **측정 대상**은 모델과 agent harness의 조합이다. 평가를 실행·기록·채점하는 evaluation harness도 구분한다.
- **완료 증거**는 transcript와 outcome을 나눈다. 예약을 끝냈다는 답변과 DB에 실제 예약이 존재하는지는 별도 검사다.
- **채점기**는 결정적 검사, 모델 rubric, 사람 검토를 조합한다. LLM judge는 사람 판단으로 보정하고 정보가 부족하면 Unknown을 허용한다.
- **경로와 결과**를 구분한다. 고정된 도구 호출 순서는 유효한 다른 해법을 거부할 수 있다. 복합 과제에는 부분 점수도 둔다.
- **반복 신뢰성**에서 pass@k는 k번 중 한 번 이상 성공, pass^k는 모두 성공을 본다. trial별 파일·캐시·git 이력이 남으면 성능이 부풀거나 실패가 서로 얽힐 수 있다.
- **평가군의 목적**도 다르다. capability 평가는 어려운 능력을 탐색하고 regression 평가는 이미 가능했던 작업의 퇴보를 감시한다.

이 구분과 운영 지침은 [원문의 평가 구조·비결정성·구축 절차](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)에 근거한다.

## 활용 맥락과 설계 질문

아래는 이 노트의 해석이다. 도구 호출을 오케스트레이션하는 런타임이나 상태를 바꾸는 백엔드의 회귀 평가에 적용할 수 있다.

| 검사 대상 | 남겨야 할 증거 | 별도로 판단할 것 |
| --- | --- | --- |
| 결과의 정확성 | 작업 전후의 대상 상태와 읽기 결과 | 완료 문장의 설득력 |
| 행동의 적절성 | 권한·필수 조건 검사와 도구 인자 | 우연히 성공한 최종 상태 |
| 반복 실행의 신뢰성 | 초기 상태, 각 trial 결과, 실패 원인 | 한 번 얻은 최고 결과 |

결과 중심 채점도 권한·보안 절차를 생략할 이유는 아니다. 필수 불변조건과 자유롭게 선택할 구현 경로를 먼저 나누는 편이 좋다. 부분 점수는 실패를 진단하는 값으로 쓰고, 필수 조건의 실패가 평균 점수에 묻히지 않도록 성공 판정은 별도로 둔다.

## 한계와 해석 범위

원문은 팀의 실무 경험을 정리한 가이드이며 특정 평가법의 우위를 입증하는 통제 실험 논문은 아니다. 소개된 CORE-Bench 사례도 채점 수정과 scaffold 변경이 함께 있어 한 요소의 효과로 돌릴 수 없다. 자동 평가가 실제 사용 분포를 대표한다고 보장할 수 없으므로 운영 관찰과 사람 검토를 함께 권한다.

이 노트에서도 상태 검사만으로 작업 의미 전체를 판정할 수 있다고 보지 않는다. 검사기가 보는 상태가 무엇인지, 불확실한 외부 응답을 어떤 결과로 남길지까지 과제별로 정의해야 한다.

## 작은 검증 제안

실행하지 않은 제안이다. 공개 합성 과제를 대상으로 별도 승인된 실험에서 확인할 수 있다.

1. 완료 문구는 같지만 실제 상태는 성공·미변경·부분 변경인 사례를 만들어 응답 채점과 상태 검사의 누락을 비교한다.
2. 동일한 정상 결과에 서로 다른 허용 도구 경로를 붙여 검사기가 유효한 대안을 잘못 거부하는지 본다. 권한 위반 경로는 별도 실패 사례로 둔다.
3. 초기 상태를 고정한 반복 실행 계획을 만들고 trial별 결과와 pass@k·pass^k를 함께 기록한다. 공통 인프라 장애는 에이전트 실패와 분리한다. 소수 반복의 수치를 운영 신뢰성 추정으로 일반화하지 않는다.

**남은 질문:** 사용자가 원하는 성공 조건 중 자동으로 확인할 수 있는 부분과 사람 판단이 필요한 부분은 어디에서 나뉘는가?
