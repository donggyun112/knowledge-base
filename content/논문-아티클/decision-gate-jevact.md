# Decision Gate — 실행 전 검증과 제한된 재수정의 효과와 한계

**JevAct는 에이전트가 낸 제안을 실행하기 전에 일부 검사하고, 문제가 있으면 제한된 횟수만큼 다시 제안하게 하는 하네스다.** 정형 상태는 코드로 계산하고 대화 해석은 별도 판단 모델에 맡긴다는 분리가 핵심이다. 그러나 논문의 실행 계약은 위험한 행동을 끝까지 차단하는 보안·권한 경계와 다르다.

> [!info] 자료와 검토 상태
> Iftach Shoham, Yuval David 외, *Think Before You Act: Decision Gate for LLM Agents*. arXiv v1 발행 **2026-10-28**, 수집 **2026-11-01 KST**. [초록·버전 이력](https://arxiv.org/abs/2610.38620)과 [v1 본문·부록](https://arxiv.org/html/2610.38620v1)을 검토했다. **Techniques / Assess · 읽기 전**. 아래 수치는 저자 보고이며 재현 실험은 하지 않았다.

## 1. 제안과 실행 사이에 무엇이 들어가는가

ReAct 모델, 기본 프롬프트와 도구는 그대로 둔다. 하네스의 한 단계는 다음 순서다.

1. **Propose:** 에이전트가 메시지나 도구 호출을 제안한다.
2. **Trigger:** 쓰기 호출 또는 작업을 포기하거나 사람에게 넘기는 hand-off인지 판별한다. 검사 대상이 아닌 제안은 그대로 진행한다.
3. **Check:** 검사기는 pass 또는 flag와 구체적인 피드백을 돌려준다.
4. **Commit / revise:** 통과하면 실행한다. flag된 제안은 실행하거나 대화 이력에 저장하지 않고, 일시적인 피드백을 붙여 다시 제안하게 한다.

Kev는 다음 행동을 선택하는 주체가 아니다. 행동은 원래 에이전트가 고르고, Kev는 후보에 관한 질문을 판정한다. 피드백도 해당 재제안에만 사용하며 장기 대화 이력에 누적하지 않는다. [§3.1–3.2](https://arxiv.org/html/2610.38620v1#S3.SS1)

## 2. 오프라인 정책 컴파일과 온라인 검사를 분리한다

| 단계 | 입력과 산출물 | 읽을 때 주의할 점 |
| --- | --- | --- |
| 오프라인 컴파일 | 도메인 정책·도구 스키마 → 도구별 yes/no 질문, Boolean 허용 규칙, 상태 계산 Python 코드, hand-off 체크리스트 | 자동 생성된 검사가 정책 전체를 올바르게 담는다는 보장은 없다 |
| 개발 로그로 보정 | 예시 도구 결과로 코드 생성·한 차례 수리, 질문과 체크리스트 일부 제외 | 필터와 체크리스트 구성도 성능에 영향을 준다 |
| 온라인 코드 검사 | 제안 인자와 이전 도구 결과에서 날짜·금액·개수 등 계산 | 정형 사실의 계산을 모델 추론에 맡기지 않는다 |
| 온라인 모델 검사 | 정책·대화·도구 결과·제안에 관한 고정 선택지 질문 | 확률적 해석이며 실제 권한 증명이나 승인 토큰이 아니다 |

실험의 컴파일러는 Claude Opus 4.6, 판단기는 **Kev-27B**다. Kev는 생성형 설명을 출력하지 않고 한 번의 forward pass로 선택지 확률을 반환하는 prefill-only 모델이다. 같은 문맥의 질문들이 pass를 공유한다. 다만 이 설명을 문맥 길이와 질문 수에 무관한 전체 시스템 비용 보장으로 확대하면 안 된다. [§3.3–3.4, §4.3](https://arxiv.org/html/2610.38620v1#S3.SS3)

부록의 필터도 중요하다. 개발 쓰기 호출에서 확신한 위반으로 너무 자주 작동하는 질문을 제외하고, hand-off는 성공한 개발 에피소드에서 불필요하게 작동하는 항목을 제거한다. 후자는 outcome 정보를 사용하므로 전체 파이프라인을 완전히 label-free라고 부르면 부정확하다. 또한 Telecom의 테스트 분리는 필터에 관한 것이며 체크리스트 자체는 결과 검토 뒤 수정했다고 명시한다. [부록 A.1](https://arxiv.org/html/2610.38620v1#A1.SS1)

## 3. 왜 hard authorization gate가 아닌가

> [!warning] 실패 시 닫히는 승인 장치로 해석하지 말 것
> 쓰기 검사는 재수정 예산 **2회**, hand-off는 **1회**다. 예산이 소진되면 **다음 제안을 추가 검사 없이 실행**한다. 이는 무한 차단을 피하는 설계이지, 위반 행동이 실행되지 않는다는 보장이 아니다.

수정 요청은 이미 실행된 쓰기 호출을 재시도하는 것이 아니다. 아직 실행하지 않은 **제안**을 버리고 새로 만드는 과정이다. 외부 부수 효과의 중복 실행, 멱등성, 트랜잭션 복구를 해결한 것으로 읽어서는 안 된다. [§3.2](https://arxiv.org/html/2610.38620v1#S3.SS2)

쓰기 질문은 **P(yes) ≤ 0.05일 때만 no**, 나머지는 yes로 취급한다. 따라서 사용자가 요청하거나 동의했는지 애매한 상황도 질문 단계에서는 통과 쪽으로 분류될 수 있다. 다른 코드 검사와 Boolean 규칙이 제안을 flag할 수는 있지만, 이 문턱 자체는 명시적 승인을 요구하는 정책이 아니다. 판단 확률의 보정이나 정확성도 보장되지 않는다. [§3.5](https://arxiv.org/html/2610.38620v1#S3.SS5)

부록에서 생성된 검사 코드의 예외는 **위반 없음**으로 처리한다. 필요한 기록이 없을 때도 해당 사실을 건너뛰게 한다. 이 역시 운영용 fail-closed 권한 검사와는 다른 계약이다. [부록 A.1, Step 3](https://arxiv.org/html/2610.38620v1#A1.SS1)

## 4. 결과는 어디에서 좋아졌고 어디에서 불분명한가

평가는 같은 에이전트 모델을 쓰는 ReAct와 전체 JevAct 하네스를 비교한다. τ²-bench는 Airline **50개 과제**, Telecom **114개 과제**, BFCL multi-turn은 **800개 항목**이다. 주 결과는 과제당 세 번 실행한다.

- **pass@3:** 세 번 중 한 번 이상 성공한 과제 비율.
- **pass^3:** 세 번 모두 성공한 과제 비율.

두 지표를 바꾸어 읽으면 “더 반복 가능해졌다”를 “더 많은 문제를 풀었다”로 오해할 수 있다. [§4, Table 2](https://arxiv.org/html/2610.38620v1#S4)

| 설정 | 저자 보고 | 해석 범위 |
| --- | --- | --- |
| Telecom, GPT-4.1 사용자 시뮬레이터 | 8개 에이전트 모두 두 지표 개선. 모델 평균 pass@3 +16.0%p, pass^3 +16.9%p | 전체 하네스 효과이며 hand-off 검사나 Kev만의 인과 효과는 아님 |
| Airline | 6개 중 pass@3은 4개 개선·1개 동일·1개 하락, pass^3은 4개 개선·2개 하락 | 50개 과제라 과제 하나가 2%p. 일괄적 개선으로 설명하기 어려움 |
| BFCL | 9개 모두 pass^3 개선, pass@3은 4개 개선·5개 하락 | 반복 성공률과 과제 커버리지는 다르게 움직임 |
| Telecom 사용자 시뮬레이터 변경 | gpt-oss-120b 사용 시 pass^3 변화 −1.8%p, 95% CI −7.9~+4.4%p | 기존 개선이 나타나지 않음. 사용자 시뮬레이터 의존성을 숨기면 안 됨 |

출처: [§5 및 §6](https://arxiv.org/html/2610.38620v1#S5). 이 결과는 벤치마크 기반이며 실제 고객 환경이나 보안 공격 상황의 성능을 측정한 결과가 아니다.

## 5. 추가 호출 때문인가, 판단이 좋아서인가

Airline의 GPT-4.1 단일 시행 ablation에서 ReAct 50.0%, 전체 검사 72.0%, 코드 검사만 68.0%, Kev 질문만 57.1%였다. 이 설정에서는 정형 코드 검사가 개선의 상당 부분을 설명한다. 단일 시행 결과를 안정적인 순위로 단정해서는 안 된다.

별도 대조에서 GPT-4.1은 무조건 재검토보다 선택적 검사가 유리했지만, gpt-oss-120b는 재검토 기회만으로도 전체 검사와 같은 향상을 보였다. 따라서 모델별로 **검사 내용의 가치와 단순 추가 추론 기회의 가치**를 분리해야 한다. [§5.1](https://arxiv.org/html/2610.38620v1#S5.SS1)

또한 라벨이 있는 개발 쓰기 호출 260개 중 잘못된 호출은 101개였는데, 그중 42개는 컴파일된 질문을 위반하지 않았다. 정책 준수와 사용자가 실제 원한 행동의 정확성이 일치하지 않는다는 한계다. [§6 및 부록 A.4](https://arxiv.org/html/2610.38620v1#S6)

## 6. 설계에 가져올 부분과 별도로 만들어야 할 부분

다음은 논문 구현을 그대로 설명한 것이 아니라 **운영 설계에 대한 제안**이다.

- **가져올 부분:** 제안 객체와 실행을 분리하고, 정형 사실 검사를 먼저 수행한 뒤 대화 의도처럼 해석이 필요한 부분만 모델에 맡긴다. flag에는 무엇을 고칠지 구체적인 근거를 붙인다.
- **별도 권한 경계:** 명시적 사용자 승인, 도구 권한, 대상 리소스 범위는 재수정 예산과 관계없이 집행한다. 판단기 오류·timeout·불확실성의 처리도 명시한다. 위험한 행동은 모델의 낙관적 확률만으로 승인하지 않는다.
- **복구·감사:** 제안 ID, 검사 버전, 사용한 상태, 판정과 실행 결과를 별도로 남긴다. 모델 대화에 피드백을 누적하지 않는 것과 감사 기록을 남기지 않는 것은 다른 결정이다.
- **평가 대조군:** baseline, 코드만, 모델만, 전체 검사, 무조건 재수정과 비슷한 빈도의 무작위 재수정을 비교한다. 과제 성공뿐 아니라 미탐·오탐, 불필요한 hand-off, 총 지연·추가 호출 비용을 함께 본다.

### 다음 질문

1. 예산 소진 후 무검사 실행 대신 중단·승인 요청으로 바꾸면 성공률과 잘못된 실행률은 어떻게 달라지는가?
2. 정책상 허용되지만 사용자 의도와 다른 호출을 어떤 명시적 상태와 테스트로 잡을 것인가?
3. 사용자 시뮬레이터, 문맥 길이와 정책 개정이 바뀌어도 임계값과 체크리스트가 유지되는가?
