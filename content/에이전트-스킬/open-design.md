# OpenDesign — 코딩 에이전트를 디자인 작업공간으로 확장하기

OpenDesign은 이미 사용하는 코딩 에이전트에 디자인 규칙과 미리보기 화면을 연결하는 오픈소스 작업공간이다. 자연어로 화면을 설명하면 에이전트가 프로토타입을 만들고, 결과를 보면서 같은 프로젝트를 고쳐 나가는 흐름을 제공한다. 읽을 때 중심에 둘 질문은 **“어느 모델이 더 예쁜 화면을 만드나”보다 “생성한 화면을 어떻게 일관되게 수정하고 개발로 이어 가나”**다.

원문 페이지 제목은 “Best Open Source Claude Design Alternative”다. 여기서 *Best*는 공급자의 포지셔닝이며 독립적인 비교 평가 결과가 아니다. 이 글은 2026년 10월 19일 공식 사이트와 공개 저장소 문서를 읽고 정리했다. 앱 설치, 디자인 생성, 내보내기와 협업 기능은 직접 시험하지 않았다.

## 왜 이런 작업공간이 필요한가

화면 하나를 생성하는 것과 제품의 여러 화면을 같은 디자인으로 유지하는 것은 다른 문제다. 예를 들어 대시보드를 만든 뒤 설정 화면과 소개 페이지를 추가한다고 생각해 보자. 매번 프롬프트에서 색상·글꼴·간격을 다시 설명하면 수정할 때마다 기준도 흩어지기 쉽다. 생성물을 이미지로만 받으면 개발자가 실제 화면을 다시 구현해야 한다.

OpenDesign이 제안하는 해법은 디자인 기준과 생성 파일을 프로젝트 안에 남기는 것이다. [공식 README](https://github.com/nexu-io/open-design#readme)에 따르면 디자인 시스템의 중심은 `DESIGN.md`다. 새로운 형식의 패키지에는 토큰 CSS, 컴포넌트, 자산과 출처 정보도 들어갈 수 있다. 에이전트는 이 기준을 읽어 HTML 기반 산출물을 만들고, 작업공간은 그 파일을 미리보기로 보여 준다.

이 구조의 의미는 생성 결과를 다음 작업의 입력으로 다시 쓸 수 있다는 데 있다. 다만 디자인 규칙을 제공한다고 해서 모델이 모든 규칙을 항상 지킨다는 보장은 없다. 일관성은 결과를 검토해야 확인할 수 있다.

## 어떻게 돌아가는가

로컬 CLI 경로에서는 사용자의 코딩 에이전트가 파일을 작성한다. OpenDesign은 별도의 만능 모델이라기보다, 에이전트 실행과 디자인 문맥, 결과 확인을 묶는 층에 가깝다. README는 이를 플러그인, 스킬, 디자인 템플릿, 디자인 시스템으로 나눈다. 각각 작업 흐름, 에이전트의 행동 지침, 출력 구조, 브랜드 기준을 담당한다.

실행 과정을 더 구체적으로 보여 주는 자료는 [에이전트 어댑터 문서](https://github.com/nexu-io/open-design/blob/88b3d9931419fed946aab0717b7054042a6a91be/docs/agent-adapters.md)다. 데몬은 설치된 실행 파일과 사용 가능 기능을 확인하고, 선택한 스킬의 본문을 프롬프트에 조합한다. 스킬 디렉터리는 프로젝트 전용 사본으로 준비한다. 실행 결과는 텍스트, 도구 호출, 파일 변경 등의 공통 이벤트로 변환해 화면에 전달한다. Codex 경로는 기본적으로 설치된 CLI의 app-server를 사용한다고 문서화되어 있다.

따라서 “여러 에이전트를 지원한다”는 말에는 서로 다른 의미가 섞일 수 있다. OpenDesign이 직접 실행하는 런타임과, 외부 에이전트가 MCP로 OpenDesign을 이용하는 연결은 구분해야 한다. 실제 호환성은 이름이 목록에 있는지만으로 판단하지 말고 연결 방식과 버전을 확인해야 한다.

## 사용 흐름을 한 장면으로 이해하기

신규 서비스의 대시보드를 설명하는 상황이라면, 먼저 디자인 시스템과 화면의 목적을 정한다. 그다음 에이전트가 만든 HTML을 열어 정보 배치와 탐색 흐름을 확인한다. “그래프를 더 크게”처럼 모호한 요청을 반복하기보다, 어떤 정보를 먼저 읽어야 하는지와 수정할 화면을 지정하는 편이 검토 기준을 만들기 쉽다.

[공식 사이트](https://open-design.ai/)는 자연어 수정 외에도 요소 이동·크기 조절·텍스트와 색상 편집을 소개한다. 파일을 개발 도구로 넘기거나 HTML·PDF·PNG로 내보낼 수 있고, 슬라이드는 편집 가능한 PowerPoint 출력도 안내한다. Figma 내보내기는 지원하지 않는다고 명시한다.

이 흐름은 이해관계자에게 클릭 가능한 초안을 보여 주거나, 개발 전 화면의 정보 구조를 좁혀 갈 때 잘 맞는다. 반면 프로토타입이 열리는 것만으로 서비스가 완성된 것은 아니다. 인증, 실제 데이터 연결, 접근성, 반응형 동작, 보안과 테스트는 별도 검증 대상이다.

## 비용과 데이터 경계를 먼저 이해해야 한다

사이트는 실행 방식을 로컬 코딩 에이전트, 개인 API 키를 쓰는 BYOK, OpenDesign Cloud로 구분한다. 무료 데스크톱 앱을 쓰더라도 에이전트 구독이나 모델 API 비용은 별개다. Cloud는 계정과 모델 크레딧을 사용하는 경로다. 따라서 “오픈소스이므로 생성 비용도 없다”는 해석은 맞지 않는다.

**로컬 우선이라는 표현도 완전한 오프라인 처리를 뜻하지 않는다.** [PRIVACY.md](https://github.com/nexu-io/open-design/blob/88b3d9931419fed946aab0717b7054042a6a91be/PRIVACY.md)는 프로젝트와 생성 파일을 로컬에 두더라도 모델 기능은 선택한 제공자에 의존한다고 설명한다. 어떤 문맥이 어느 서비스로 나가는지는 사용 경로에 따라 확인해야 한다.

이 문서는 제품 분석과 품질 추적이 기본 활성화되어 있고 설정에서 선택 범위를 줄이거나 끌 수 있다고 안내한다. 선택적 수집에는 프롬프트, 응답, 도구 입출력 같은 대화·도구 내용도 포함될 수 있다. 별도로 텔레메트리 목적지가 설정된 빌드의 안전·신뢰성 진단은 항상 활성화되며 일반 분석 스위치로 꺼지지 않는다고 명시한다. README의 간략한 동의 기반 설명만 보고 모든 수집이 기본 비활성이라고 판단하면 안 된다.

또한 어댑터 문서는 일부 CLI를 비대화형 권한 모드로 실행한다고 설명한다. 작업 디렉터리를 지정했다는 사실과 파일시스템 격리는 같지 않다. 민감한 저장소를 연결하기 전에는 사용하려는 에이전트의 실제 권한 경계를 검토할 필요가 있다.

## 문서끼리 다른 부분은 어떻게 읽을까

조사 시점에도 다음 설명은 완전히 일치하지 않았다.

- **BYOK의 파일 편집:** 사이트 FAQ는 개인 API 키로 생성은 가능하지만 프로젝트 파일 편집에는 로컬 에이전트를 쓰라고 안내한다. README는 파일 도구가 없는 API 실행과 파일 기반 CLI 실행을 구분하고, 어댑터 문서는 OpenCode 프로세스를 이용하는 BYOK 경로를 설명한다. 따라서 “BYOK는 언제나 파일 편집 불가”처럼 일반화하지 않고, 선택한 실행 경로의 도구 권한을 확인해야 한다.
- **팀 협업의 제공 상태:** 사이트 FAQ는 팀 작업공간과 댓글을 소개하지만 기능 카드에는 출시 소식을 받으라는 문구도 남아 있다. 소개된 협업 흐름 전체가 모든 요금제와 버전에서 즉시 가능하다고 단정하기 어렵다.
- **설치와 지원 범위:** [웹 Quickstart](https://open-design.ai/quickstart/)는 Node.js 24와 pnpm 10.33.2를 요구한다. 그런데 그 페이지에 나오는 에이전트 목록과 현재 어댑터 문서의 런타임 목록도 다르다. 도입할 때는 사용하는 릴리스의 설치 문서와 실제 설정 화면을 다시 확인해야 한다.

이 차이는 기능이 없다는 증명도, 정상 동작한다는 증명도 아니다. 홍보 페이지를 그대로 기능 명세로 쓰지 않아야 한다는 근거다.

## 어떤 경우에 검토할 만한가

이미 코딩 에이전트를 사용하고, 디자인 기준을 파일로 관리하며, HTML 초안을 개발로 이어 가고 싶다면 검토할 만하다. 반대로 Figma 중심의 편집·전달이 필수이거나 설치와 권한 관리 없이 완성된 운영 서비스를 기대한다면 요구사항부터 맞춰 봐야 한다.

비교의 기준은 생성 예시의 화려함보다 **두 번째 수정이 얼마나 쉬운가**다. 같은 디자인 시스템으로 여러 화면을 만들었을 때 규칙이 유지되는지, 한 화면을 바꿨을 때 다른 화면을 훼손하지 않는지, 내보낸 파일을 실제 개발자가 이어서 사용할 수 있는지를 확인하는 것이 유용하다. 이는 도입 판단을 위한 제안이며 이 글에서 수행한 실험 결과는 아니다.
