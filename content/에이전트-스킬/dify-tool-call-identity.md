# Dify 도구 호출 ID — 스트림 슬롯과 이력의 식별자를 구분하기

같은 도구를 한 응답에서 두 번 호출하면 각각 결과를 돌려줘야 한다. 반대로 다음 스트림 청크에 다시 나타난 호출은 새 실행이 아니라 기존 호출의 인자 갱신일 수 있다. Dify의 수정은 플러그인 ID 하나를 두 경우의 판정과 대화 이력에 그대로 쓰면 생기는 문제를 보여준다.

- **수집·검증일**: 2026-11-22 KST
- **공개 시점**: 2026-11-12 PR 병합, 2026-11-18 Dify 1.20.0 릴리스
- **검증 범위**: 병합된 변경과 회귀 테스트 코드, 릴리스 노트 정적 검토. 실행·재현·모델 호출은 하지 않았다.

## 병합된 수정이 나누는 세 가지

| 경계 | 최종 변경 |
| --- | --- |
| 스트림 슬롯 | 한 청크에서 같은 공급자 ID가 여러 번 나오면 등장 순번을 붙여 구별한다. 이후 청크에 같은 ID와 순번이 다시 나오면 같은 슬롯을 갱신한다. |
| 내부 이력 | 응답을 처리하기 전에 이전 모델 응답의 호출 ID를 예약해 현재 응답에서 재사용하지 않는다. 최근 결과를 남기는 이력 압축에서 오래된 결과와 최근 결과가 같은 ID로 함께 지워지는 일을 막기 위해서다. |
| 공급자에 다시 보낼 메시지 | 바뀐 내부 ID에 원래 공급자 ID를 메타데이터로 남겨, 어시스턴트의 호출과 그에 대응하는 도구 결과·재시도 메시지를 공급자 형식으로 되돌릴 때 복원한다. |

최종 변경에는 한 청크의 병렬 호출뿐 아니라 누적 청크 갱신, 이력의 JSON 왕복, 여러 응답에서 같은 플러그인 ID를 쓸 때 최근 결과가 압축에서 남는지를 확인하는 회귀 테스트 코드가 포함된다.

## 적용할 때 확인할 점

이 방식은 Dify 게이트웨이가 전체 또는 누적 인자 스냅샷을 보내는 계약에 맞춰져 있다. 같은 ID 하나가 별도 청크에 연달아 오면 새 호출로 추측하지 않고 같은 슬롯을 갱신한다. 순번을 바꾸는 다른 전송 계약에 그대로 적용할 수 있다는 근거는 없다. 내부 이력 ID가 겹치지 않는다고 해서 재시도·장애 이후 외부 쓰기가 한 번만 실행되는 것도 아니다. 그 보장은 [[에이전트-스킬/idempotent-api-retries|멱등성 계약]]으로 따로 확인해야 한다.

작은 검증을 한다면 가짜 게이트웨이와 부작용 없는 도구에서 세 입력을 비교할 수 있다. 같은 ID로 서로 다른 인자 두 개가 한 청크에 왔을 때는 호출 두 개, 누적 청크가 반복됐을 때는 같은 두 슬롯, 다음 응답에서 ID가 재등장했을 때는 별도 이력 ID를 기대한다. 직렬화 전후 공급자에 보내는 원래 ID와 이력 압축 뒤 남긴 최근 결과도 따로 확인한다.
