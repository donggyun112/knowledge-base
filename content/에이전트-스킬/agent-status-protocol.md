# ASP — 에이전트의 상태를 누가 보고하고, 누가 판단하는가

에이전트에게 일을 맡겼는데 답이 없다. 오래 걸리는 모델을 호출 중일 수도 있고, 사용자 승인을 기다릴 수도 있고, 프로세스가 죽었을 수도 있다. 상위 에이전트 입장에서는 모두 같은 침묵처럼 보인다. 반대로 “정상 작동 중”이라는 신호는 계속 오는데 실제 작업은 같은 단계를 반복할 수도 있다.

**Agent Status Protocol(ASP)은 이런 상황을 여러 런타임이 같은 의미로 보고하고 관찰하기 위한 상태 규약 제안이다.** 에이전트 대신 일을 실행하거나 답의 정확성을 평가하는 기술은 아니다. 핵심은 상태를 표현하는 어휘, 전달하는 이벤트, 신호가 없거나 보고가 충돌할 때의 처리 규칙을 함께 정한다는 것이다.

> [!info] 이 글의 기준
> 2026년 10월 19일 [논문 v1](https://arxiv.org/html/2610.21538v1)과 [공식 저장소](https://github.com/AgentStatusProtocol/spec)를 읽고 정리했다. ASP 0.1은 논의를 위한 작업 초안이며 승인된 표준이 아니다. 저장소 구현도 설명용 예제다. 이 글은 구현을 실행하거나 성능을 검증한 결과가 아니다. 아래의 가상 사례와 설계 제안은 원문의 규칙과 구분했다.

## 먼저 전체 흐름부터

ASP의 기본 경로는 **런타임 또는 어댑터 → 상태 서버 → 관찰자**다. 여기서 런타임은 모델 호출·도구 실행·작업 대기를 관리하는 프로그램이고, 어댑터는 기존 시스템의 신호를 ASP 형식으로 바꾸는 연결 코드다. 관찰자는 사람용 대시보드일 수도, 작업을 분배하는 오케스트레이터나 다른 에이전트일 수도 있다.

1. **등록한다.** 에이전트 또는 어댑터가 `register`로 식별자와 heartbeat 간격 등을 알린다.
2. **상태를 보고한다.** 작업 시작·승인 대기·완료 같은 변화는 작은 JSON 이벤트로 `POST /v1/events`에 보낸다. 여러 이벤트를 묶는 `/v1/events:batch`도 있다.
3. **상태 서버가 정리한다.** 인증과 이벤트 순서를 확인하고 현재 상태를 갱신한다. heartbeat가 끊겼는지, 외부의 격리 결정이 자기 보고보다 우선하는지 등도 처리한다.
4. **관찰자가 읽는다.** `GET /v1/agents`로 현재 상태의 스냅샷을 받고, `GET /v1/stream`의 SSE로 이후 변화를 구독한다. 개별 에이전트 스냅샷도 제공한다.
5. **필요한 조치를 다른 시스템이 수행한다.** 예를 들어 오케스트레이터가 격리된 에이전트에 새 작업을 보내지 않는다. ASP는 상태를 전달하며, 실제 차단·취소·복구 동작은 연결된 시스템이 담당한다.

SSE는 서버가 클라이언트에 변화를 계속 보내는 HTTP 스트림이다. 따라서 대시보드가 모든 에이전트에게 번갈아 “지금 뭐 해?”라고 물을 필요가 없다. 서버는 보통 보고를 받는 쪽이고, 선택적인 능동 health probe만 예외다.

별도 서버를 반드시 새로 띄워야 하는 것은 아니다. 상태 집계·생존 판단·권한 우선순위·배포 기능을 기존 오케스트레이터 안에 넣을 수도 있다. **상태 서버라는 역할이 필요하다는 것과 독립된 서버 프로세스가 필요하다는 것은 다르다.** HTTP POST와 SSE는 초안의 참조 연결 방식이다. [논문 §4, §8](https://arxiv.org/html/2610.21538v1#S4)

## 하나의 status 값으로는 부족한 이유

`status = running`만으로는 “프로세스는 살아 있지만 공급자 호출 제한에 걸렸고, 현재 작업은 승인을 기다리는 중”을 표현하기 어렵다. ASP는 상태를 다섯 축으로 나눈다.

| 축 | 답하는 질문 | 예시 | 범위 |
| --- | --- | --- | --- |
| lifecycle | 에이전트가 운영상 어떤 단계에 있는가? | `idle`, `busy`, `at-capacity`, `unreachable`, `crashed` | 에이전트당 하나 |
| health | 어떤 문제로 기능이 제한되는가? | `healthy`, `degraded`, `rate-limited`, `stalled` | 에이전트당 하나 |
| task | 이 작업은 어디까지 왔는가? | `working`, `awaiting-approval`, `delegated`, `completed` | 작업마다 하나 |
| floor | 이 대화에서 발언권은 어떤 상태인가? | `joined`, `requesting-floor`, `has-floor`, `floor-revoked` | 대화마다 하나 |
| governance | 참여·권한·신뢰에 어떤 제한이 걸렸는가? | `normal`, `sandboxed`, `quarantined`, `under-review` | 에이전트당 하나 |

각 축은 기본적으로 독립적이다. `busy`이면서 `degraded`일 수 있고, 작업 하나는 `working`, 다른 작업은 `awaiting-approval`일 수 있다. `at-capacity`는 더 받을 여력이 없는 정상적인 운영 상태다. 큐가 과도하게 쌓인 health의 `overloaded`와 구분한다.

`floor`는 도구 실행 권한이나 일반적인 자원 잠금이 아니다. 여러 참여자가 있는 대화에서 누가 발언권을 요청·보유·반납했는지를 뜻한다. 그런 대화가 없는 시스템에는 이 축을 억지로 만들 필요가 없다. governance도 선택적 차원이다.

task 상태는 A2A의 기존 상태를 재사용하면서 `queued`, `awaiting-approval`, `delegated`, `retrying`, `timed-out`을 추가한다. OFP는 floor 상태의 연결 대상이고, OpenTelemetry는 추적·지표와 연결된다. 세 기술을 ASP가 대체한다는 뜻은 아니다. [논문 §5, §9](https://arxiv.org/html/2610.21538v1#S5)

## 서브에이전트가 직접 보고하나, 시스템이 알아서 판단하나?

**둘 다 있지만, 같은 종류의 판단을 하는 것은 아니다.** “에이전트가 보고한다”를 “LLM이 매번 자기 상태를 문장으로 작성한다”로 읽으면 오해하기 쉽다.

### 1. 실행 중인 사실은 런타임이나 어댑터가 보고한다

작업 큐에 넣었는지, 도구 호출이 끝났는지, 승인 요청을 만들었는지는 실행 코드가 이미 알고 있는 사건이다. 이런 사건을 상태 전이로 연결할 수 있다. 원문은 네이티브 보고와 어댑터를 모두 허용한다. 따라서 상태 보고를 위해 매번 LLM 추론을 한 번 더 수행해야 하는 구조가 아니다.

다만 어댑터가 보지 못한 사실까지 추측해서는 안 된다. 예를 들어 대화 메시지만 관찰하는 어댑터는 발언권을 얻었다는 사실은 알지만, 침묵하는 동안 모델 호출 중인지 도구 대기 중인지 멈췄는지는 알 수 없다. 원문은 관찰할 수 없는 축을 추측하기보다 보고하지 않도록 권고한다. [논문 §9.2.1](https://arxiv.org/html/2610.21538v1#S9.SS2.SSS1)

### 2. 상태 서버는 신호와 규칙으로 일부 상태를 추론한다

heartbeat 간격을 10초로 등록했다면 기본 규칙에서 25초 동안 자기 이벤트가 없을 때 lifecycle을 `unreachable`로 바꾼다. 이는 “연결되지 않는다”는 판단이지, 충돌 원인을 알아냈다는 뜻은 아니다. 실제 비정상 종료를 감지한 supervisor는 `crashed`를 보고할 수 있다.

자기 자신이 보낸 다른 이벤트도 heartbeat로 계산하지만, 다른 구성요소가 그 에이전트를 관찰해 보낸 이벤트는 대신 계산하지 않는다. `unreachable`일 때 마지막 task와 floor는 지워 버리기보다 오래된 정보(stale)임을 표시해 남기도록 권고한다. 살아 있는 신호가 돌아오면 lifecycle을 그 이벤트의 값으로, 값이 없으면 `online`으로 복원한다. [논문 §7.1](https://arxiv.org/html/2610.21538v1#S7.SS1)

### 3. 외부 관찰과 권한 있는 판단을 함께 보존한다

다른 에이전트가 “호출이 계속 timeout 난다”고 보고해도 상대의 자기 보고 `healthy`를 곧바로 덮어쓰지는 않는다. 서버는 둘을 함께 노출해 불일치를 볼 수 있게 한다. 반면 governance에는 **operator > guardrail > self**라는 우선순위가 있다. guardrail이 설정한 격리를 대상 에이전트가 `normal`이라고 보고해 해제할 수 없다. 같은 수준 이상의 권한이 필요하다.

이 우선순위를 모든 축의 단일 서열로 일반화해서는 안 된다. lifecycle의 서버·supervisor 판정, health의 peer 관찰, governance의 제한은 서로 다른 규칙으로 처리된다. `source` 문자열을 적는 것만으로 권한이 생기는 것도 아니다. 서버는 인증된 주체가 다른 에이전트에 대해 보고하거나 제한을 설정할 권한이 있는지 확인해야 한다. [논문 §7.2.3, §12](https://arxiv.org/html/2610.21538v1#S7.SS2.SSS3)

## heartbeat와 progressSeq는 무엇이 다른가?

heartbeat는 “보고 경로가 아직 응답한다”는 신호다. `progressSeq`는 작업 단계를 완료할 때 증가시키는 진행 카운터다. 원문 예시는 모델 호출 완료, 도구 호출 완료, 메시지 전송을 진행 단계로 든다. heartbeat를 별도 스레드에서 보내면 본 작업이 멈춰도 신호만 살아 있을 수 있으므로, 원문은 주 작업 루프에서 보내도록 권고한다.

진행 감지는 선택 기능이다. `stallAfterSec`를 선언한 에이전트는 매 heartbeat에 `progressSeq`를 넣어야 한다. 서버가 이 기능을 구현한다면 다음 조건을 함께 본다.

- `working` 또는 `retrying`인 작업이 하나 이상 있다.
- `stallAfterSec` 동안 `progressSeq`가 증가하지 않았다.
- 그러면 health를 `stalled`로 설정해 관찰자에게 알린다.

`input-required`, `awaiting-approval`, `delegated`, `queued`처럼 의도적으로 기다리는 작업 자체는 이 정체 판정을 유발하지 않는다. 다만 승인 대기 작업과 별개로 실행 중인 다른 작업이 있다면 그 에이전트에 진행이 기대될 수 있다. 또 **정상 대기를 stall에서 제외하는 것과 heartbeat 의무를 없애는 것은 다르다.**

중요한 한계가 있다. **카운터가 증가한다고 목표를 향한 의미 있는 진전이 검증된 것은 아니다.** 같은 검색을 반복하거나 잘못된 도구를 계속 호출해도 단계 완료 신호는 생길 수 있다. ASP 자체가 결과의 정확성, 반복의 유용성, 목표 달성을 자동 평가하지는 않는다. 그 검증은 별도 평가기·정책·관찰 로직의 몫이다. 긴 미디어 생성 같은 정상 작업도 있으므로 시간 기준은 작업 특성에 맞춰 정해야 한다. [논문 §7.2.1](https://arxiv.org/html/2610.21538v1#S7.SS2.SSS1)

## 가상 사례: 승인 대기와 실제 정체를 구분하기

아래는 논문의 규칙을 설명하기 위해 만든 가상 흐름이다. 특정 제품의 구현 결과가 아니다.

| 장면 | 보고하거나 관찰한 사실 | 상태를 읽는 방법 |
| --- | --- | --- |
| 조사 작업 시작 | task가 `working`, heartbeat 수신 | 실행 중이며 보고 경로도 살아 있다 |
| 자료 수집 단계 완료 | `progressSeq` 증가 | 실행 단계가 끝났다. 조사 품질까지 검증되지는 않았다 |
| 사용자 승인이 필요해짐 | task가 `awaiting-approval` | 오래 기다리는 것 자체를 정체로 보지 않는다 |
| 승인이 도착해 작업 재개 | task가 다시 `working` | 다시 진행이 기대되는 구간이다 |
| heartbeat는 오지만 카운터가 멈춤 | 정해 둔 시간 동안 진행 없음 | 선택적 진행 감지 기능이 health를 `stalled`로 판정한다 |
| heartbeat도 끊김 | 등록 간격의 2.5배 동안 자기 이벤트 없음 | lifecycle은 `unreachable`, 마지막 작업 정보는 stale로 표시한다 |

승인을 몇 시간 기다리기 위해 프로세스를 종료하는 런타임은 한 가지를 더 결정해야 한다. 일회성 프로세스의 생존과 계속 존재하는 논리적 작업을 어떻게 구분할 것인가?

원문 §4.4는 짧게 실행되는 stateless 에이전트 대신 지속되는 오케스트레이터나 호스팅 플랫폼이 어댑터로 보고하는 방식을 권고한다. 이를 장기 승인 대기에 적용해, **지속되는 supervisor가 논리적 작업의 대기 상태를 보고하도록 만드는 것은 설계 제안**이다. ASP가 승인 요청을 저장하고, 나중에 프로세스를 복원하고, 중복 실행을 방지해 주는 것은 아니다.

## 이벤트 순서와 실행 재개를 혼동하지 말자

ASP의 이벤트에는 `eventId`, `seq`, `ts`가 있다. 비슷해 보이지만 역할이 다르다.

- `eventId`: 같은 이벤트를 재전송했을 때 중복 반영하지 않기 위한 식별자다.
- `seq`: 대상 에이전트와 보고 주체의 조합별로 증가하는 순서다. 모든 주체가 공유하는 하나의 전역 카운터가 아니다.
- `ts`: 사건 시각이다. 타임스탬프만 믿고 최신 상태를 결정하지 않는다.

서버는 이미 처리한 `eventId`를 다시 처리하지 않고 202를 반환한다. 같은 보고 주체의 이전 `seq`가 늦게 도착하면 기록에는 남기되 현재 상태를 덮어쓰지 않는다. 관찰자용 SSE의 `id`는 이와 별도의 **서버 시퀀스**이며, 재연결 시 `Last-Event-ID`로 놓친 갱신을 받는 데 쓰인다.

이것은 상태 전달의 중복·순서 문제다. 도구 호출의 부작용이 정확히 한 번만 실행되도록 하거나, 재시작 후 어디부터 일을 이어 갈지 정하는 보장은 아니다. 실행 intent/done 기록, durable checkpoint, 재시도 정책, 부작용의 idempotency는 별도 실행 설계가 필요하다. 상태 이력을 남긴다는 규정만으로 특정 저장소의 장애 복구 내구성이 보장되지도 않는다. [논문 §6.1, §8, §12](https://arxiv.org/html/2610.21538v1#S8)

## 상태를 계속 넣으면 상위 LLM의 문맥이 오염되지 않나?

그럴 수 있다. 모든 heartbeat와 모든 전이를 대화 메시지처럼 상위 LLM에 누적하면, 중요한 결과보다 운영 잡음이 많아질 수 있다. 하지만 **SSE 구독은 LLM 프롬프트에 자동으로 넣는다는 뜻이 아니다.** 프로그램이 상태를 갱신하거나 대시보드가 화면을 바꾸는 것만으로도 관찰자가 된다.

원문은 이벤트에 프롬프트·모델 출력·사용자 데이터·비밀정보를 넣지 않도록 요구한다. `reason`도 짧은 코드와 중립적인 설명을 위한 필드다. 이는 데이터 최소화 규칙이지, LLM 문맥 관리 알고리즘은 아니다. ASP는 모델에게 언제 어떤 상태를 보여 줄지, 토큰 예산을 얼마로 할지, 문맥 오염이 얼마나 줄어드는지를 규정하거나 검증하지 않는다. [논문 §4.1, §12](https://arxiv.org/html/2610.21538v1#S12)

**이 글의 설계 제안**은 다음과 같다.

1. 원시 상태 스트림은 런타임의 상태 저장소에서 처리한다.
2. 상위 LLM에는 완료·실패·승인 필요·정체처럼 다음 판단을 바꾸는 변화만 전달한다.
3. 재계획 시에는 오래된 이벤트를 전부 붙이기보다 현재 스냅샷과 필요한 변화만 제공한다.
4. 보고 주체, 관찰 시각, stale 여부를 남겨 자기 주장과 외부 관찰을 구분한다.
5. 상태는 신뢰할 수 있는 지시문이 아니라 관찰 데이터로 다룬다. `reason`이나 확장 필드의 자유 텍스트를 명령처럼 실행하지 않는다.

이 방식은 ASP를 이용한 통합 설계의 한 예다. “ASP를 쓰면 문맥 오염이 해결된다”는 논문의 실험 결과로 읽어서는 안 된다.

## 그냥 내부 enum과 이벤트로 만들면 안 되나?

**단일 런타임이라면 충분히 가능하다.** 같은 팀이 모든 구성요소를 만들고 `waiting`의 의미, timeout 조건, 보고 권한을 일관되게 관리한다면 내부 enum과 이벤트로 필요한 기능을 구현할 수 있다. ASP가 없어서 원리적으로 불가능한 기능은 아니다.

문제는 경계를 넘을 때다. A 프레임워크의 `running`은 프로세스 생존을 뜻하고, B 프레임워크에서는 작업 수행을 뜻할 수 있다. 한쪽은 사용자 대기를 정체로 처리하고, 다른 쪽은 외부 격리를 자기 보고로 해제할 수 있다. JSON 모양만 맞춰도 의미가 다르면 공통 대시보드와 운영 정책은 계속 예외 처리를 요구한다.

ASP의 제안 가치는 **상태 이름뿐 아니라 신호 부재, 중복과 순서, 독립 관찰, 권한 충돌의 의미까지 공통 계약으로 만드는 데 있다.** 새로운 모니터나 새 프레임워크가 연결될 때 각각의 내부 상태 머신을 다시 학습해야 하는 비용을 줄이려는 접근이다. OpenTelemetry에 사용자 정의 이벤트를 넣어 비슷한 구조를 만들 수도 있지만, 그 경우에도 그 의미와 처리 규칙은 별도로 합의해야 한다. [논문 §1.3–1.5, §1.10](https://arxiv.org/html/2610.21538v1#S1)

따라서 도입 판단도 단계적으로 할 수 있다. 한 런타임에서는 다섯 축의 어휘와 보고 출처를 참고하는 것부터 시작하고, 다른 팀·프레임워크·운영 도구를 연결할 필요가 커질 때 이벤트 형식과 처리 규칙을 맞추는 편이 합리적이다. 이는 이 글의 판단이며, 부분적으로 참고한 시스템을 곧바로 ASP 전체 준수 구현이라고 부를 수는 없다.

## 무엇을 가져가고, 무엇은 별도로 만들어야 하나

| 가져갈 수 있는 관점 | 여전히 별도 설계·검증이 필요한 부분 |
| --- | --- |
| 운영 상태와 작업 상태를 분리한다 | 실제 작업의 성공·품질 판정 |
| 정상 대기와 진행 정체를 구분한다 | 작업별 시간 기준, 반복·무의미한 진행 감지 |
| 자기 보고와 외부 관찰을 함께 본다 | 탐지기의 정확도, 오탐 처리, 권한 발급 |
| 격리 결정의 출처와 우선순위를 남긴다 | 도구 접근 차단, 라우팅 중단, 프로세스 제어 |
| 공통 이벤트와 관찰 경로를 만든다 | 영속 저장, 복구, 실행 재개, 부작용 중복 방지 |
| 필요한 상태를 조회할 수 있게 한다 | LLM에 넣을 정보의 선택과 문맥 관리 |

공식 저장소는 Python 상태 서버·에이전트·stateless 어댑터 예제를 제공하지만, 이를 적합성 시험을 거친 참조 구현이나 운영용 구현이라고 하지 않는다. 논문도 독립 구현 검증, 적합성 테스트, 규모 확장과 보안 평가를 앞으로의 과제로 둔다. 처리량이나 정확도 향상을 입증한 성능 연구로 읽으면 안 된다.

결론적으로 ASP는 **“에이전트를 더 똑똑하게 실행하는 방법”보다 “여러 에이전트의 운영 상황을 서로 같은 뜻으로 읽는 방법”**에 가깝다. 상태를 정확히 보고하고, 서로 다른 출처의 주장을 구분하고, 필요한 시스템이 그 상태를 바탕으로 행동하도록 경계를 만드는 데 참고할 만하다.
