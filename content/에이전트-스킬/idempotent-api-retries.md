# 멱등 API — 재시도에서 같은 의도를 식별하는 계약

**상태를 복구하는 것과 외부 작업을 안전하게 다시 호출하는 것은 별개의 문제다.** 타임아웃 뒤 재시도를 설계할 때 읽을 자료다.

## 원문 핵심

같은 인자가 같은 의도를 뜻하지는 않는다. 동일한 서버 두 대를 만들 수도 있으므로, 요청 인자의 해시만으로 중복을 판정하면 정상 요청을 합칠 수 있다. 글은 **호출자와 호출자가 제공한 요청 ID**로 재시도를 식별하는 계약을 설명한다.

이 계약에는 키 저장 외의 조건도 있다.

- 요청 ID 기록과 실제 변경이 분리되어 실패하면 중복이나 누락이 생긴다. 글은 이 작업들에 ACID 성질이 필요하다고 강조한다.
- 재시도에 단순히 ‘이미 존재함’을 반환하면 호출자는 누가 만든 결과인지 다시 판단해야 한다. 의미상 동등한 응답이 클라이언트 복구를 단순하게 한다.
- 같은 ID에 다른 인자가 오면 기존 요청의 재시도로 조용히 처리하지 않고 불일치를 검증한다.
- 늦은 요청을 처리하려면 기록 보존 기간이 필요하다. EC2 사례는 리소스 수명과 이후의 추가 기간을 고려한다. 모든 서비스에 같은 TTL을 적용하라는 뜻은 아니다.

출처: [원문의 설계 설명과 예시](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). 의미상 동등함은 응답 바이트나 리소스의 현재 상태까지 항상 같다는 뜻이 아니다.

## 에이전트 실행에 적용해 볼 질문

아래는 원문의 측정 결과가 아니라 **이 노트의 설계 해석**이다. 모델이 도구 인자를 다시 생성할 수 있는 런타임에서는 ‘실행 시도’와 ‘논리적 작업’을 따로 추적하는 편이 검토하기 쉽다.

1. 같은 작업을 재개할 때 기존 ID를 어디서 복원하는가? 새 시도마다 ID를 발급하면 어떤 중복 방지 경계가 사라지는가?
2. 재제안으로 대상이나 수량이 바뀌면 새 의도인가, 기존 요청의 수정인가? 승인 대상과 요청 ID를 함께 비교할 수 있는가?
3. 외부 서비스가 멱등 키를 받지 않는다면 응답 소실 뒤 무엇으로 성공 여부를 확인하는가? 확인 수단이 없을 때 불확실 상태를 어떻게 사용자에게 전달하는가?

[[langgraph-persistence|실행 상태와 장기 메모리]] 노트와 함께 읽으면, 체크포인트에 남길 실행 위치와 외부 서비스가 보장해야 할 효과의 경계를 나누어 볼 수 있다.

## 작은 검증 제안 — 아직 실행하지 않음

실제 서비스 대신 합성 요청을 받는 로컬 모형으로 계약표를 먼저 작성한다.

| 입력·실패 조건 | 관찰할 항목 |
| --- | --- |
| 첫 변경 직후 응답 소실, 같은 ID로 재시도 | 효과 수와 호출자에게 반환되는 결과 |
| 같은 인자, 다른 ID | 의도적으로 요청한 두 작업이 합쳐지는지 |
| 같은 ID, 다른 인자 | 충돌을 드러내는 오류와 변경 여부 |
| 기록 저장·효과 적용 사이의 중단 | 키만 남거나 효과만 남는 상태의 처리 |
| 보존 기간 경계의 지연 요청 | 재실행 여부와 만료 계약의 일치 |

성공 응답 수만 세지 말고 실제 효과 수, 충돌 판정, 미확정 상태를 각각 기록한다. 이 표는 제안이며 테스트 통과나 채택 근거가 아니다.

## 한계와 다음 판단

공식 경험 글이지 특정 에이전트나 SDK의 보장 증명은 아니다. 서로 다른 외부 시스템의 변경을 하나의 DB 트랜잭션으로 묶을 수 있다고 가정해서는 안 된다. 멱등 키 유무뿐 아니라 제공자의 적용 범위·보존 기간·인자 충돌·결과 조회 계약을 확인해야 한다.
