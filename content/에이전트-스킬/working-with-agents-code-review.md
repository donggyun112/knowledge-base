# 우리는 어떻게 에이전트와 일해야 하는가

> [!abstract] 핵심 관점
> 에이전트가 더 많은 코드를 만들수록 사람은 모든 줄을 읽는 데 시간을 쓰기 어렵다. 대신 **무엇을 만들지 결정하고, 실패를 잡을 검증 체계를 설계하며, 증거의 빈틈을 판단하고, 배포 결과를 책임지는 일**에 집중해야 한다.
>
> Claude Code 팀의 사례는 리뷰를 없애자는 이야기가 아니다. 검토를 개발 전 과정에 배치하고, 위험에 따라 인간의 개입을 달리하며, 놓친 문제를 빠르게 되돌리고 다음 평가에 반영하는 운영 방식이다.

## 이 문서의 읽는 법

사용자가 제공한 기사 전문과 [공개 원문](https://claude.dev/blog/solving-code-review-at-anthropic/)을 바탕으로 중요한 논점·운영 규칙·수치·한계를 한국어로 재구성했다.

- **1–10절:** 저자들이 설명한 Claude Code 팀의 운영 사례.
- **11절:** 원문이 제안하는 도입 순서.
- **12절:** 우리 업무에 적용하기 위한 이 문서의 해석과 체크리스트.
- 수치는 저자 보고이며, 여기서 독립적으로 재현한 결과가 아니다.
- 원문 그림을 복제하지 않았다. 아래 흐름도는 본문 설명을 토대로 새로 정리한 것이다.

---

## 1. 왜 에이전트 시대에는 리뷰의 목적부터 다시 물어야 하나

### 코드 생산량이 커지면 사람의 읽기 속도가 병목이 된다

저자들은 Claude Code 코드의 **약 90%를 Claude가 작성한다**고 설명한다. 그렇다면 질문은 “사람이 코드를 읽기는 하는가?”를 넘어, “이 속도로 나오는 변경을 누가, 어떤 방식으로 검증하는가?”가 된다.

서로 다른 범위의 수치를 혼동하지 않아야 한다.

| 대상 | 원문이 보고한 변화 | 해석할 때 주의할 점 |
| --- | --- | --- |
| Claude Code 코드베이스 | 6월부터 9월 사이 병합 PR 수가 두 배를 넘는 수준으로 증가 | 코드의 총량·난도나 개발자 생산성의 인과 효과를 직접 측정한 수치는 아니다 |
| Claude Code 코드베이스 | 되돌려야 했던 PR의 비율이 40% 넘게 감소 | 되돌림 **비율**의 상대 감소다. 40%포인트 감소나 사고 완전 제거가 아니다 |
| Anthropic 모노레포 | 하루 반영 변경이 5월 약 2,500건에서 9월 30,000건 이상으로 증가 | Claude Code는 이 모노레포가 아니라 **별도 저장소**에 있다 |

이 수치는 운영 변화와 함께 관찰된 자체 보고다. 특정 리뷰 도구 하나가 개선을 전부 일으켰다는 통제 실험으로 읽어서는 안 된다.

### 코드 리뷰에는 두 가지 일이 있다

1. 배포 전에 문제를 찾아 고친다.
2. 팀이 코드베이스의 구조와 변경 내용을 함께 이해하게 한다.

원문은 첫 번째를 중심으로 다루되, 기계가 대부분의 코드를 읽게 되었을 때 두 번째를 어떻게 유지할지도 별도로 설명한다.

따라서 질문을 바꾼다.

> 사람이 읽었는가보다, 이 변경에서 무엇이 잘못될 수 있고 그것을 어떤 자동 검사 또는 인간 검토가 잡아야 하는가?

리뷰 시점도 바뀐다. 코드를 완성한 뒤 PR 끝에서 기다리는 한 번의 관문보다, 작성하는 동안 계속 실행되는 검사에 가까워진다. 사람이 보기 전에 이미 Claude의 검토와 수정을 한 차례 이상 거친 변경이 대부분이라는 설명이다.

## 2. 최적화 대상은 인간의 시간과 주의력이다

원문에서 인간 비용은 두 부분을 합친다.

- 리뷰에 쓰는 시간
- 잘못된 코드가 만든 문제를 고치는 시간

첫 번째가 줄어도 두 번째가 늘면 비용을 없앤 것이 아니라 뒤로 옮긴 것이다.

### 목표와 안전 지표를 함께 둔다

Claude Code의 CLI·데스크톱·웹·모바일 저장소에서 목표로 하는 상태는 **대부분의 PR이 작성자 자신을 포함해 최대 한 명의 인간이 관여하는 경로로 병합되되, 되돌림과 사고가 늘지 않는 것**이다. 모든 PR을 무인 병합한다는 선언이 아니다.

| 측정 대상 | 보는 이유 |
| --- | --- |
| PR당 인간 승인 수의 중앙값과 95백분위 | 보통의 부담과 꼬리 구간의 부담을 함께 본다 |
| 인간 댓글 | 사람이 직접 개입하는 정도를 본다 |
| 사람을 기다리는 시간 | 변경이 인간의 응답 때문에 멈추는 시간을 본다 |
| 되돌림·사고 비율 | 검토 부담 절감이 사후 피해 증가로 바뀌지 않는지 감시한다 |

주의력을 아끼는 목적은 사람이 할 일을 없애는 데 있지 않다. 팀에는 새로운 문제와 인간이 판단해야 할 일이 계속 남는다.

## 3. 변경 하나의 생애: 여섯 검증 층과 복구 안전망

원문은 여섯 층의 검사 아래에 롤백을 두며, 본문에서는 빠른 탐지·복구를 일곱 번째 항목으로 설명한다.

```text
요청·구현
  ↓
① PR 전 실행 검증과 독립된 맥락의 검토
  ↓
② PR AI 리뷰 + ③ 보안 리뷰 + ④ CI
  ↓
⑤ 위험과 신뢰 조건에 따른 인간 승인
  ↓
⑥ 병합 큐 → 내부 사용·기능 플래그 → 단계적 공개
  ↓
⑦ 탐지·대응·복구
  └─ 사고를 평가 데이터와 지침·검사 개선으로 환류
```

위 그림은 개념적인 연결이다. 모든 검사가 정확히 이 순서로 직렬 실행된다는 뜻은 아니다. 각 층에는 놓치는 문제가 있으므로 한 층만으로 완벽을 기대하지 않는다.

### ① PR을 만들기 전: “완료했다” 대신 실행 결과를 보여 준다

에이전트에게 실행 가능한 확인 수단을 준다.

- 테스트
- 빌드
- 디자인과 비교할 화면 캡처
- 브라우저나 휴대전화 시뮬레이터에서의 동작 확인

그다음 구현 맥락을 그대로 공유하지 않는 서브에이전트가 새로운 맥락에서 diff를 검토한다. 저자들은 이 두 습관을 자신들의 모범 사례 가이드와 연결한다.

많은 팀원은 PR 전에 버그 탐색, diff 단순화, 종단 간 동작 확인용 내부 스킬도 실행한다. UI 변경은 디자인 지침과 비교한다.

Boris Cherny가 검증 수단을 주는 일이 결과를 **2–3배 더 좋게 만든다고 추정**했다는 설명도 나온다. 이것은 이 글에서 제시한 통제 실험의 성능 배수가 아니라 개인의 추정이다.

### 반복 지적은 개별 수정에서 운영 규칙으로 옮긴다

같은 문제가 계속 발견되면 스킬·린트 규칙·지침 파일을 개선한다.

| 파일 | 담을 내용 | 원문이 강조하는 작성 방식 |
| --- | --- | --- |
| `CLAUDE.md` | 기술 스택, 관례, 목표와 비목표 | 매번 로드되므로 짧게 유지하고 상세 문서는 연결한다 |
| `REVIEW.md` | 코드 소유자가 정한 해당 영역의 리뷰 기준 | 실제 실패의 정의, 사소한 지적 제한, 제외 경로, 파일·행 근거, 명확한 요약 |

`CLAUDE.md`의 관례를 어기는 코드뿐 아니라, 변경으로 인해 그 파일의 설명이 낡아지는 경우도 리뷰 대상이다.

좋은 `REVIEW.md`는 “좋은 코드를 작성하라”처럼 막연하지 않다. 문서에서는 거짓 설명이 실패이고, 설정에서는 잘못된 경로 지정이 실패라는 식으로 무엇을 잡아야 하는지 정한다. 이름만 보고 추측하는 대신 파일·행의 증거를 요구하며, 요약은 발견 건수부터 시작하고 문제가 없을 때도 없다고 명확히 말하도록 한다. 리뷰어가 이 지침을 실제 따르는지도 따로 확인한다.

### ② 모든 PR에 AI 리뷰를 붙인다

사람이 보기 전에 Claude가 PR을 검토한다. 변경분만 따로 읽는 것이 아니라 전체 저장소와 PR의 의도를 함께 보고 다음을 묻는다.

- 원래 문제를 해결하는가?
- 기존 시스템과 맞는가?
- 다른 부분을 깨뜨리는가?
- 버그 수정이라면 근본 원인을 해결하는가?

원문은 공개 Code Review가 Team·Enterprise에서 일반 제공되고, `/code-review`는 더 가벼운 로컬 검토를 실행한다고 설명한다. 이는 글에서 설명한 시점의 제품 상태이며 도입할 때는 현재 문서를 확인해야 한다.

리서치 프리뷰 도입 당시 **실질적인 리뷰 댓글을 받은 내부 PR 비율이 16%에서 54%로 증가**했다. 이것을 버그 탐지 정확도나 오탐률로 바꾸어 읽으면 안 된다. 원문은 1,000줄 넘는 PR 대부분에는 발견사항이 있고, 작은 PR 대부분은 문제없이 돌아온다고도 설명한다.

관리자는 저장소별로 Quick·Standard·Deep을 선택한다. 놓친 버그의 비용이 추가 리뷰 시간보다 큰 영역에서는 깊은 검토가 가치 있다는 판단이다.

### 발견과 확증을 분리한다

여러 에이전트가 병렬로 버그를 찾고, 별도 그룹이 각 발견사항을 검증·투표한다. 충분한 동의를 받은 항목만 게시한다.

스타일·진단·정리만을 위한 발견사항은 걸러내며, 이런 필터는 내부 PR에서 A/B 테스트한 뒤 채택했다고 한다. 남은 항목은 심각도순 인라인 댓글로 나타난다.

댓글에는 Important·Nit·Pre-existing 같은 분류가 붙는다. 특히 이미 존재하던 문제를 이번 PR 작성자가 만든 문제처럼 보이게 하지 않는 것이 중요하다. 원문은 사소한 지적 필터링과 Nit 분류를 모두 설명하지만, 분류별 세부 임계값은 제시하지 않는다.

발견사항은 모두 응답 대상이다. 고치거나, 스레드를 해결 처리하면서 이유를 남겨야 한다. 밤사이 에이전트가 수정까지 맡아 다음 날 이미 한 차례 더 검토된 PR을 받는 경우도 있다.

### ③ 보안 리뷰는 병합을 막을 수 있어야 한다

보안은 별도의 자동 검토를 거친다. 일반 버그 리뷰 또는 보안 리뷰의 발견사항이 열린 채로 남아 있으면 병합할 수 없다.

- 실제 문제면 수정한다.
- 오탐이면 짧은 이유를 남기고 해결 처리한다.
- 이후 커밋이 문제를 고치면 해당 발견사항은 자동으로 해소될 수 있다.

원문은 오픈소스 보안 리뷰 GitHub Action이나 `/security-review`를 도입 경로로 안내한다.

### ④ CI와 PR 설명은 계속 필요하다

린트·타입 검사·플랫폼별 테스트·빌드는 기본 방어선이다. 일반적인 CLI PR도 사람이 보기 전에 수십 개 검사를 거칠 수 있다.

PR 템플릿에는 **어떻게 테스트했는지, 어떻게 되돌릴지**를 적는다. Claude가 내용을 채울 수는 있어도, 변경을 요청한 사람이 확인 책임을 진다.

### ⑤ 인간 승인은 위험에 비례시킨다

| 위험 | 원문의 예시 | 요구되는 인간 승인 |
| --- | --- | --- |
| 낮음 | 문서·문구, 내부 전용 기능, 플래그 뒤의 추가적 변경 | 자동 리뷰와 보안 검사를 통과하면 요구하지 않을 수 있다 |
| 중간 | 일반 제품 변경, 캐싱·자동 업데이트·시스템 프롬프트 같은 민감 영역의 변경 | 한 명 |
| 높음 | 가장 위험한 코드와 항상 두 사람을 요구하는 일부 경로 | 두 명 |

이 표만 복사하면 중요한 조건을 놓친다.

1. **등급은 작성자가 아니라 변경 내용으로 정한다.** 첫 분류기가 위험을 정하고, 별도 분류기가 등급과 무관하게 이 변경에 추가 사람이 필요한지 확인한다.
2. **일부 경로는 사람을 반드시 요구한다.** 소유자가 민감하다고 지정한 경로와 CI 워크플로 파일 등이 해당한다.
3. **완화된 경로는 신뢰 목록의 작성자에게만 적용한다.** 주로 해당 저장소를 소유한 팀이다. 그 외에는 두 번째 사람의 승인이 필요하다.
4. **에이전트 승인은 인간 승인 자리를 채우지 못한다.** 자동 검사는 저위험 변경을 통과시킬 수 있지만, 사람이 필요한 자리를 봇으로 대체할 수는 없다.
5. **에이전트에게 작업을 시킨 사람이 책임진다.** 그 사람은 직접 코드를 작성했을 때처럼 요구되는 리뷰어 중 한 명으로 계산한다.
6. **승인은 특정 커밋에만 유효하다.** 에이전트의 추가 push나 수동 충돌 해결 등 시스템이 안전성을 보증하지 못하는 새 커밋이 들어오면 다시 승인해야 한다.

중위험 예시에 민감 영역이 있다고 해서 그 영역 전체가 언제나 중위험이라는 뜻은 아니다. 구체적인 변경과 필수 경로 규칙이 함께 적용된다.

### ⑥ 병합 이후에도 단계적으로 노출한다

병합 큐는 변경을 main에 적용한 상태로 검사를 다시 실행한다. 각자 통과한 두 PR이 결합하면서 깨지는 상황을 방어하기 위한 장치다.

새 동작은 보통 기능 플래그 뒤에서 직원에게 먼저 제공한다. 내부에서 많이 사용하면서 외부 사용자보다 먼저 회귀를 발견할 수 있다. 공개 릴리스는 `latest` 채널에 먼저 나가고 `stable`은 뒤따른다.

### ⑦ 놓친 문제는 빨리 발견하고 되돌린다

검증을 거쳐도 실수는 발생한다.

- 기능 플래그는 재배포 없이 끌 수 있다.
- Claude Code에는 주간 온콜 순환이 있다.
- 사고 회고에서는 어느 검증 층이 문제를 잡았어야 했는지 묻는다.
- 작성자·온콜·되돌림 및 사고 대시보드가 탐지를 담당한다.

**아직 없는 장치도 명시한다.** 되돌림이나 사고 지표가 나빠질 때 승인 요구를 자동으로 강화하는 회로 차단기는 아직 없다. 엔지니어들은 더 많은 코드를 무인 병합으로 옮기기 전에 이런 장치를 원한다고 한다.

원문에 인용된 동료는 속도를 낮추면 오류가 줄지만, 많은 부분은 모든 일을 덜 하기 때문이라고 지적한다. 처리량 감소와 변경당 품질 개선을 구분해야 한다는 문제의식이다. 원문은 속도를 낮추는 것만으로 안전을 확보하기보다, 문제를 알아차리고 고치는 속도를 높이는 데 무게를 둔다. 이를 실패를 방치해도 된다는 의미로 해석해서는 안 된다.

## 4. 리뷰어도 평가하고 개선해야 한다

### 실제 사고를 평가 데이터로 만든다

과거 사고를 일으킨 PR, 후속 수정, 되돌림을 모은다. 해당 코드를 아는 엔지니어가 버그가 실제 있었는지와 위치를 확인한다. 리뷰어는 이 데이터로 **매일 평가**된다.

사고가 늘면 평가 집합도 확장된다. 리뷰어의 프롬프트·도구·모델이 바뀔 때에는 기존 평가 전체를 대상으로 다시 점수를 낸다.

### 많이 잡는 것과 잘 잡는 것은 다르다

오탐을 개의치 않으면 발견 건수를 늘리기는 쉽다. 그래서 댓글에 대한 실제 반응을 구분한다.

| 반응 | 의미 |
| --- | --- |
| 고쳤다 | 수정할 가치가 있다고 받아들인 발견 |
| 틀렸다고 판단했다 | 오탐이라고 판단한 항목 |
| 의도된 동작이라고 설명했다 | 코드 의도와 리뷰 해석의 불일치 |
| 중요하지 않다고 판단했다 | 비용에 비해 수정 가치가 낮은 항목 |

이미 깨끗하다고 아는 PR에도 리뷰어를 실행한다. 불필요한 지적으로 **해로운 수정을 유발할 만한 항목**을 얼마나 내놓는지 센다.

우선순위는 실제 버그 탐지가 먼저이고, 그다음이 검토 반복 횟수 감소다. 잡음 감소를 위해 중요한 버그를 놓치는 방향을 목표로 삼지 않는다.

## 5. 에이전트끼리의 리뷰는 반드시 수렴해야 한다

### 사람에게 작은 지적도 에이전트에게는 큰 작업이 될 수 있다

사람은 사소한 지적을 몇 초 만에 넘길 수 있다. 에이전트 작성자는 그 지적을 수정하고, 새 커밋을 만들고, 다시 리뷰를 요청할 수 있다. 작성 에이전트와 검토 에이전트가 서로 계속 일을 만드는 루프가 생긴다.

실제로 한 CLI PR은 밤사이 **50회 넘는 리뷰·수정**을 반복한 뒤 사람이 중단했다.

팀이 반복 지적 대상을 git blame으로 확인했더니 **약 59%는 첫 검토 때부터 존재하던 코드**였다. 매회 새로 만든 버그를 찾는 것이 아니라, 원래 있던 문제를 조금씩 추가 발견하는 경우가 많았다는 설명이다.

“59%가 모든 코드의 기존 버그였다”거나 “전체 PR의 59%가 실패했다”는 뜻은 아니다.

### 재검토 정책을 바꾼다

팀도 매번 새로운 것이 나온다는 이유로 여러 차례 리뷰를 기본으로 실행하며 문제를 키웠다고 인정한다. 위험한 변경에는 가치가 있을 수 있지만 모든 PR에 같은 방식이 적절한 것은 아니다.

그래서 재현율뿐 아니라 **통과까지 필요한 리뷰 횟수**도 추적한다.

| 조치 | 의도 |
| --- | --- |
| 세 차례 이후 접근 자체를 다시 생각하도록 요청 | 같은 방식의 수정 반복을 멈추고 해결 전략을 재검토 |
| 초기 몇 차례 이후에는 새 diff 중심으로 재검토 | 전체 기존 코드에서 발견사항을 조금씩 끌어오는 현상을 줄임 |
| 한 줄이 아니라 버그 유형을 지적 | 같은 유형의 다른 사례도 한꺼번에 해결 |
| 이미 게시한 발견사항을 반복하지 않음 | 중복 작업과 재논쟁을 줄임 |

**세 번이면 무조건 통과하거나 종료한다는 규칙은 아니다.** 세 차례 뒤에 작성자에게 접근 재고를 요청하는 장치다.

기존 코드를 살피는 작업은 야간 리뷰 에이전트가 별도로 수행한다. 현재 PR의 완료와 기존 코드의 광범위한 개선을 같은 반복 루프에 무한히 묶지 않는 방식으로 이해할 수 있다. 마지막 문장은 이 문서의 해석이다.

## 6. 사람이 계속 맡아야 하는 다섯 가지 일

| 인간의 역할 | 남겨야 하는 판단 |
| --- | --- |
| 만들지 결정 | 방향·취향·범위. 이것이 필요한 변경인가? |
| 위험한 코드 검토 | 과금·자동 업데이트·CI 등 실패 비용이 큰 부분 |
| 아키텍처 검토 | 다른 사람이 복사할 패턴이나 구조가 타당한가? |
| 증거 읽기 | 테스트 출력, 실행 명령과 반환값, 화면, 발견사항이 무엇을 입증하는가? |
| 결과 책임 | 누가 작성했든 배포된 변경의 결과를 누가 책임지는가? |

리뷰 병목이 해결되었다고 말한 팀도 외부 팀에서 오는 변경에는 사람 리뷰를 유지했다. 기술적으로 구현 가능한지뿐 아니라 **애초에 해야 하는 일인지**를 묻는 사람이 필요하기 때문이다.

증거를 읽을 때 특히 중요한 기준은 다음이다.

> 검사가 무엇을 놓칠 수 있는지 설명할 수 없다면, 빠른 승인 대신 제대로 된 리뷰를 요청한다.

사람은 단순 승인 버튼으로 남아서는 안 된다.

## 7. 사람이 모든 diff를 읽지 않으면 팀은 코드를 어떻게 이해하나

리뷰의 두 번째 역할인 공동 이해는 별도 문제다. 원문은 이 부분에 **공식 절차가 없다**고 명시한다. 완성된 지식 관리 제도를 운영한다고 과장해서는 안 된다.

팀의 접근은 다음과 같다.

- 누구도 Claude Code 전체의 완전한 정신 모형을 갖고 있지 않으며, 반드시 그럴 필요도 없다고 본다.
- 수정하려는 정확한 부분에 대해 Claude에게 설명문을 요청한다.
- 설명은 현재 코드를 바탕으로 몇 분 안에 만들어질 수 있다.
- 일부는 해당 부분을 시각화하는 작은 학습용 산출물도 만든다.
- 공개 Slack 채널에서 일하며 다른 사람이 무엇을 만드는지 본다.

예를 들어 전체 저장소를 막연히 설명해 달라고 하기보다 “관리 설정을 어떻게 가져오는가?”처럼 특정 동작을 묻는다.

핵심은 학습을 포기하는 것이 아니라 **곧 변경할 모듈을 이해하는 데 학습 시간을 집중하는 것**이다. 한 줄 문구 변경의 diff를 읽는 일이 주는 학습 가치와, 변경할 모듈의 구조 설명을 읽는 가치는 다를 수 있다.

## 8. 배포한 사람이 책임지되, 책임을 비난으로 만들지 않는다

작거나 중간 규모의 변경을 반영한 뒤 문제가 생기면, 보통 그 변경을 반영한 사람이 고친다는 팀 규범이 있다.

이 규범은 개인의 성실함만으로 성립하지 않는다.

| 기반 조건 | 책임을 감당할 수 있게 하는 이유 |
| --- | --- |
| 작은 변경 | 검토·디버깅·되돌림이 쉽다 |
| 되돌릴 수 있는 배포 | 플래그·revert·단계적 릴리스로 대부분의 실수를 빠르게 되돌린다 |
| 영향 범위에 맞는 검증 | 피해 비용이 큰 코드는 더 많은 사람과 검사를 붙인다 |
| 빠른 관측 | 텔레메트리와 내부 사용으로 회귀를 일찍 발견한다 |
| 시스템 중심 사고 회고 | 수정 책임은 맥락을 가장 잘 아는 사람에게 두되, 비난보다 시스템을 살핀다 |

책임은 공동으로도 나눈다. 공개 채널에서는 코드 소유자가 아니어도 작업을 보고 의견을 보태거나, 빈틈에 에이전트를 투입하거나, 다른 사람의 작업을 이어받을 수 있다.

따라서 “요청했으니 네 잘못”이라는 문화와는 다르다. 책임자가 명확하면서도 팀이 함께 발견하고 복구할 수 있는 환경이 필요하다.

## 9. 에이전트가 싸게 만든 코드를 버리는 것도 정상적인 결정이다

에이전트는 일을 시작하는 비용을 낮춘다. 그렇다고 시작한 모든 작업이 제품에 들어가야 하는 것은 아니다.

공개 채널에서 누군가 이유를 묻고, 과거 결정을 알려 주고, 더 단순한 방식을 제안하면 작성자는 PR을 닫거나 방향을 바꾼다. 코드를 빨리 만들었으므로 폐기를 큰 손실로 느끼지 않을 수 있다.

중요한 시점은 **완성된 PR에 뒤늦게 차단 댓글을 다는 때가 아니라, 작업 중인 대화에서 일찍 방향을 제시하는 때**다. 인간의 제품 판단을 끝단 승인에만 몰아넣지 않는다는 뜻이다.

## 10. 공개 제품과 내부 운영 정책을 구분한다

원문의 Code Review 발표는 PR 승인이 여전히 인간의 판단이라고 설명하며, 제품은 **발견사항을 게시하지 승인을 내리지 않는다**.

반면 Anthropic 내부 저장소는 소유자가 일부 저위험 변경을 자동 검사만으로 병합하도록 정할 수 있다. 이 경계는 계속 바뀌고 있다.

따라서 다음은 서로 다른 주장이다.

- AI 리뷰 제품을 설치했다.
- 우리 저장소가 어떤 변경에 인간 승인을 요구할지 정했다.
- 그 정책 아래 실제로 안전성과 비용 개선을 관찰했다.

첫 번째가 두 번째와 세 번째를 자동으로 보장하지 않는다.

리뷰가 문제를 놓치면 모델에게 어떤 정보가 없었는지를 묻고, `CLAUDE.md`·스킬·새 검사에 개선을 넣는다. 최종 목표는 변경당 인간 시간을 줄이되, 이전보다 되돌림을 늘리지 않는 것이다.

## 11. 원문이 제안하는 도입 순서

처음부터 내부 자동병합 정책 전체를 복사하기보다 한 저장소에서 기준을 조정하며 넓히라는 안내다.

### PR 전

- [ ] 에이전트가 실행할 검사를 짧은 `CLAUDE.md`에 적는다.
- [ ] 포매터·린터를 실행하는 훅을 둔다.
- [ ] 로컬 `/code-review`, `/security-review` 또는 새 맥락의 서브에이전트 검토를 사용한다.
- [ ] `REVIEW.md`를 만들고 반복 리뷰 지적을 옮긴다.

### 모든 PR

- [ ] CI를 필수로 설정한다.
- [ ] PR 템플릿에 Testing·Risk·How to revert를 넣는다.
- [ ] 한 저장소에 AI 리뷰어를 도입하고 몇 주간 기준을 조정한 뒤 확대한다.
- [ ] 보안 리뷰를 자동화하고 모든 리뷰 스레드를 해결해야 병합되게 한다.
- [ ] 실수의 비용에 맞춰 검토 깊이를 다르게 한다.
- [ ] 리뷰 반복을 제한하고 초기 몇 차례 이후에는 새 변경분을 중심으로 본다.

### 승인 정책

- [ ] 변경 내용에 따른 위험 등급을 문서화한다.
- [ ] 처음에는 엄격하게 시작하고 증거에 따라 완화한다.
- [ ] 완화 경로는 신뢰하는 작성자에게만 적용한다.
- [ ] CODEOWNERS·브랜치 보호로 인증·과금·CI·릴리스 워크플로·설치 프로그램 등에 인간을 요구한다.
- [ ] 봇 승인이 필수 인간 승인을 대신하지 못하게 한다.
- [ ] 새 커밋에 대해 기존 승인의 유효성을 다시 판단하도록 한다.

### 병합과 운영

- [ ] 병합 큐, 기능 플래그, 내부 우선 사용, 단계적 릴리스, 간단한 복구 경로를 갖춘다.
- [ ] 사고와 되돌림을 평가 집합에 넣는다.
- [ ] 리뷰어의 프롬프트·도구·모델 변경 시 다시 평가한다.
- [ ] 인간 시간을 측정하되 되돌림·사고 비율을 안전 지표로 함께 본다.

> 아래 표와 양식은 원문을 바탕으로 이 문서가 제안하는 운영 설계다. Anthropic이 그대로 사용한다는 뜻이 아니며, 효과를 직접 측정하지 않았다.

### 업무를 맡길 때 다섯 가지를 합의한다

| 합의할 것 | 질문 | 필요한 산출물 |
| --- | --- | --- |
| 목적 | 왜 해야 하고 무엇은 하지 않을 것인가? | 목표·비목표 |
| 권한 | 읽기·수정·배포 중 어디까지 허용하는가? | 실행 범위·승인 경계 |
| 증거 | 무엇을 관찰하면 성공이라고 할 것인가? | 실행 가능한 확인 조건 |
| 종료 | 어떤 상태에서 완료·재설계·질문으로 전환하는가? | 종료·중단 조건 |
| 책임 | 결과를 받아들이고 문제를 처리할 사람은 누구인가? | 담당자·후속 행동 |

성공 조건과 권한은 다르다. 목표 달성에 도움이 된다고 해서 운영 데이터나 외부 설정 변경까지 허용된 것은 아니다.

### 완료 보고를 네 상태로 나눈다

“테스트 통과” 한 줄보다 다음 상태 구분이 불확실성을 드러내는 데 유용할 수 있다.

- **확인됨:** 합의한 조건을 실제 관찰했다.
- **불일치:** 관찰 결과가 조건과 다르다.
- **미확인:** 환경·권한 등 제약으로 관찰하지 못했다.
- **적용 제외:** 이 작업에는 해당하지 않으며 이유가 있다.

검사 하나마다 상태를 붙이고 대상 커밋·환경을 함께 기록한다. 실행하지 못한 검사를 성공으로 처리하지 않는다.

### 바로 사용할 요청 양식

```text
목표:
이번에 하지 않을 것:
허용한 변경 범위와 실행 권한:
작업 전 확인할 맥락:
성공을 확인할 명령·테스트·관찰 조건:
반드시 사람이 판단할 부분:
수정 반복을 멈추고 질문하거나 재설계할 조건:
되돌리는 방법:
결과 책임자:

완료 보고:
- 실제 바뀐 동작
- 실행한 확인과 그 결과
- 미확인 항목·검사의 사각지대
- 남은 위험과 필요한 결정
```

### 도입 효과를 판단할 때 피할 오해

1. **댓글 증가를 품질 증가와 동일시하지 않는다.** 실제 수정 가치와 오탐을 함께 봐야 한다.
2. **비율 감소를 절대 건수 감소로 바꾸지 않는다.** 분모와 변경량이 다를 수 있다.
3. **사람 수 감소를 책임 감소로 바꾸지 않는다.** 결정권자와 결과 책임자는 남아야 한다.
4. **검사 통과를 안전 보증으로 바꾸지 않는다.** 어떤 실패를 확인하지 못했는지 말할 수 있어야 한다.
5. **반복을 성실함으로만 평가하지 않는다.** 완료에 가까워지는지, 기존 문제를 조금씩 더 발견하는 루프인지 구분한다.
6. **다른 팀의 운영 성과를 우리 팀의 목표 수치로 그대로 쓰지 않는다.** 변경 종류·관찰 기간·환경을 맞춘 기록부터 필요하다.

### 한 문장으로 정리하면

에이전트와 잘 일한다는 것은 더 많은 일을 시키는 기술만이 아니라, **검증 가능한 일을 맡기고, 필요한 순간에 사람이 판단하며, 실패를 복구하고 다음 작업의 조건을 개선하는 체계를 만드는 일**이다.
